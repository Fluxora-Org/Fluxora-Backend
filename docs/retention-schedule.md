# Data Retention Schedule

**Status:** current · **Applies to:** `fluxora-backend` · **Endpoint:** [`GET /api/privacy/retention`](../../src/routes/privacy.ts)

Every class of data this service persists, and how long it keeps it. This is the
document to answer a subject-access, rectification or erasure request from.

Nothing here is maintained by hand except the prose. The schedule table is
generated from `RETENTION_MANIFEST` in [`src/pii/retention.ts`](../../src/pii/retention.ts),
which is also what the purge jobs are derived from — so the period published
here and the period the code enforces cannot drift apart. `pnpm run check:retention`
fails CI if the document, the manifest, the migrations and the purge jobs disagree.

## How to read the table

| Column | Meaning |
| --- | --- |
| **Retention** | Maximum age before deletion or redaction. *Indefinite* means the service makes no deletion commitment — a reviewed decision, not an omission. |
| **Action** | `delete` removes the row, `redact` overwrites its PII columns and keeps the row for audit integrity, `expire` removes a row that has already lapsed by its own expiry column. |
| **Enforced by** | The mechanism that actually deletes the data. Anything other than `retention-purge`, `dlq-purge` and `expires-column` is not run by a scheduled job. |
| **Legal hold** | Whether a legal hold can suspend deletion of this class. Only `streams` can be held — see below. |

## What enforces the schedule

Two scheduled jobs do the deleting. Both are safe to re-run, and a run that
has nothing to do reports zero rows.

**`src/jobs/retentionPurge.ts`** — walks every `retention-purge` rule above.
For each one it computes `now − retentionDays`, selects the oldest matching
rows in batches of 500 with `FOR UPDATE SKIP LOCKED`, and deletes or redacts
them, committing each batch separately. It reads a single `now` for the whole
run, so a run spanning a month boundary still evaluates every rule against one
instant. `dryRun: true` counts candidates without writing anything.

`audit_logs` is append-only at the storage layer, so that rule is the only
delete path into it and runs under the dedicated `fluxora_retention` role (or,
in single-role deployments, a transaction-local bypass flag that no request
path ever sets).

**`src/jobs/dlqPurge.ts`** — deletes dead-letter-queue entries that are in a
terminal state (`replayed`, or `dead` with an old `last_failed_at`) and older
than the window. A recently failed entry is never touched. The window is
`DLQ_RETENTION_DAYS`, default **30 days**, configurable 1–365, and `0` disables
the purge entirely. It is capped at 365 so a typo cannot delete all history.

Two windows are configurable per deployment, and only their **defaults** are a
commitment — CI asserts the manifest against the env schema:

| Variable | Default | Bounds |
| --- | --- | --- |
| `DLQ_RETENTION_DAYS` | 30 days | 1–365, `0` disables |
| `IDEMPOTENCY_TTL_SECONDS` | 86400 (1 day) | up to 7 days |

`src/jobs/partitionMaintenance.ts` is the third job in this family, but it only
*creates* monthly partitions for `contract_events`; it never drops one. Shortening
`contract_events` retention is a deliberate, confirmed operator action
(`dropOldPartitions` in `src/scripts/db-ops.ts`, dry-run by default).

## Legal hold

A legal hold is the only thing that can suspend a retention commitment.

- **The flag is a `legal_hold` boolean column.** `streams` has one
  ([`migrations/20260724000000_streams_legal_hold.ts`](../../migrations/20260724000000_streams_legal_hold.ts)).
  It is the **only** table that does.
- **A held row is never deleted, and every skip is recorded.** The purge job
  reads `legal_hold` *inside the same transaction as the delete*, so a hold
  cannot be set in the gap between the check and the delete. For each held row
  it writes a `PURGE_SKIPPED_LEGAL_HOLD` audit event, on every run, until the
  hold is lifted.
- **A hold is released by an operator** clearing the flag; the next purge run
  then deletes the row.
- **The erasure endpoint honours holds too.** `DELETE /api/privacy/erasure/:recipientAddress`
  skips held streams and reports the count as `rowsSkippedLegalHold` rather
  than silently returning a lower number.

### Why only `streams` can be held

The purge job's hold check is a column read, so a hold can only exist where the
column exists. Tables without it are purged on schedule whether or not anyone
objects — which means **placing a hold on them would be silently ineffective.**
If a litigation hold must cover `audit_logs`, `webhook_dlq` or any other class,
the column has to be added to that table first. Do not assume this schedule
honours a hold it cannot.

`runRetentionPurge` discovers the column at runtime and substitutes a constant
`FALSE` for tables that lack it, rather than failing — which is precisely why
this distinction has to be published instead of being an implementation detail.

## Exemptions

Four places where a period is declared but nothing deletes the rows. Each is
recorded in the manifest as an `unenforcedReason`, published here, and enforced
as non-empty by CI — so an open gap cannot ship without its explanation.

**1. `webhook_outbox_items` and `webhook_deliveries` — 90 days, not enforced.**
These are live work queues, not logs. Rows in status `pending` or `in_flight`
have not been delivered yet, and the generic purge job selects purely on age, so
pointing it at these tables would silently drop undelivered webhooks. The
commitment applies to terminal rows; enforcement needs a status-scoped predicate
of the kind `dead_letter_queue` already uses. Tracked as a follow-up to #1506.

**2. `api_keys` — indefinite, operator-deleted.** A credential must stay
verifiable for exactly as long as it can authenticate. Revocation is an audited
`DELETE /api/admin/api-keys/:id` that sets `active = false`; the row is kept for
the credential-lifecycle audit trail. Only `HMAC-SHA256(pepper, salt ‖ key)`, a
per-key salt and an 8-character prefix are stored — the raw key is never
persisted, so a revoked row cannot be used to impersonate its holder.

**3. `privacy_consents` — indefinite, superseded in place.** One row per data
subject, bounded by the number of subjects rather than by traffic; each `PUT`
overwrites the existing row. A consent withdrawal must stay provable, so
consent records are superseded rather than expired.

**4. `contract_events` and derived state — indefinite, operator-shortened.**
Every row is a public Stellar ledger event that replays and reorg resolution
need. Deleting it would contradict Horizon and the contract. Dropping old
monthly partitions is available but requires an explicit environment
confirmation.

Two further classes sit outside the service and are listed for completeness
rather than enforcement: **application logs** (30 days, enforced by the log
aggregator's own configuration) and **database backups** (see below).

## Backups outlive the live database

`src/scripts/backup-retention.ts` keeps a three-tier policy: **7 days** of daily
snapshots, **28 days** of weekly, **365 days** of monthly. The monthly tier is
the binding number for this schedule, and it matters for a subject-access
response: **a subject's data can still exist inside a monthly backup for up to a
year after it was purged from the live database.** Backups are encrypted,
access-controlled, and restored into an isolated environment, so the purge job
does not touch them. Erasing from the live database is necessary but not
sufficient — say so explicitly when answering an erasure request.

## Answering a subject-access request

The data subject is identified by their Stellar recipient address, and the
service stores that address in exactly two places, both with a one-year period:

1. `streams.sender_address` / `streams.recipient_address` — redacted in place
   after 365 days, and pseudonymised at rest with `pgcrypto` (see
   [`docs/security/pii-encryption.md`](security/pii-encryption.md)).
2. Nothing else. `privacy_consents` and the erasure path use a keyed HMAC of
   the address, never the plaintext.

So a subject-access response is:

| Question | Where to look | Period |
| --- | --- | --- |
| Which streams involve this address? | `streams` (live rows) | chain state indefinite; address PII redacted at 365 days |
| What consent is recorded? | `privacy_consents`, by HMAC of the address | indefinite, superseded in place |
| What happened in the audit trail? | `audit_logs` by `resource_id` | 365 days |
| Could the data exist elsewhere? | `contract_events` / logs / backups | indefinite / 30 days / up to 365 days |

Erasure is `DELETE /api/privacy/erasure/:recipientAddress` (admin or DPO token
required). It tombstones the address columns and clears the address hashes,
preserves `amount`, `ledger`, `stream_id` and `status` for financial audit
integrity, skips legally held rows while reporting the count, and writes
`GDPR_ERASURE` and `PII_ERASURE_REQUESTED` audit events in the same
transaction. Run the retention purge afterwards to bring forward anything that
was already past its period.

The machine-readable form of all of the above is
[`GET /api/privacy/retention`](../../src/routes/privacy.ts), served from the same
manifest, and it is marked `Cache-Control: no-store`.

## Changing the schedule

1. Edit the entry in `RETENTION_MANIFEST` ([`src/pii/retention.ts`](../../src/pii/retention.ts)).
   Give a real basis for the new number in `rationale` — a regulation, a debug
   window, an unbounded-growth guard — not a restatement of the number.
2. Set `enforcement` to the mechanism that will do the deleting. If a table
   gains a `legal_hold` column, set `legalHoldExempt: true` and add it to
   `LEGAL_HOLD_EXEMPT_TABLES`; if nothing deletes the rows, write an
   `unenforcedReason`.
3. Run `pnpm run check:retention -- --write` to regenerate the table above.
4. `pnpm run check:retention` must pass, along with the test suite.

A new table with no stated period fails CI: `checkCoverage` fails on any table a
migration creates that has no manifest entry, and on any manifest entry naming a
table no migration creates.
